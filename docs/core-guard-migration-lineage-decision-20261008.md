# Core guard migration lineage decision — review proposal

**Status:** Recommend a forward-only, explicitly verified second migration track for the hosted-v3 guard. This is a design decision for review, not an implemented runner, numbered migration, schema capture, or release approval. The core candidate starts at clean `2dd491cec5f14b42465b32c3ecb7513e14c654d6`; original `0011` and optional `0012`–`0015` identities remain untouched.

- The separate feature worktree allocates `0012_warm_harpoon`–`0015_lame_franklin_storm` at journal indices 12–15 and increasing timestamps. `0012` creates presenter capture tables; `0013` derived looks references capture; `0014` adds synthetic identities; `0015` extends derived looks and references capture. Its snapshot chain descends from original `0011`.
- The read-only inventory in [core schema qualification](core-schema-qualification-20261008.md) found no `0011` or optional hashes on five queried ready databases. Ten archived Preview branches, possible undiscovered projects, and the active deployment's secret-to-database binding remain unverified. The development journal also has an extra historical draft row. These observations do not establish that optional migrations were never applied anywhere.
- Current `drizzle.config.js` has one `out` directory, and `tools/check-migrations.mjs` verifies one complete journal, one migration-set hash, and one schema lock. Installed Drizzle Kit config exposes `out` and `migrations.table/schema`; installed Drizzle ORM exposes `migrationsFolder`, `migrationsTable`, and `migrationsSchema`. These are framework capabilities, not an existing repository two-track release path. Its PG migrator compares each migration timestamp only with the latest applied `created_at`; it does not validate an older unexpected row before applying newer SQL.

## Required two-track contract before coding a numbered guard

1. **Frozen legacy lineage:** preserve original `0000`–`0011` SQL, tags, timestamps, and hashes. Preserve optional `0012`–`0015` SQL, tags, timestamps, and hashes on the optional path. Never seed, delete, or reinterpret applied journal rows. Any core migration runner must refuse an unknown legacy row and must not run the full optional folder for a core-only target.
2. **Separate core guard lane:** use Drizzle's configurable migration folder and a distinct migration schema/table for the [unnumbered guard proposal](hosted-v3-purpose-guard.proposed.sql). The runner verifies the exact legacy prerequisite before invoking this lane. No default `db:migrate` command may silently select both lanes. The guard's own hash and journal entry are created only after this mechanism passes local review.
3. **Explicit modes and dependencies:** core mode requires the exact legacy `0000`–`0011` journal, the exact core-guard journal, a 27-table catalogue with the additional guard, and absence of optional tables. Optional mode may accept the exact legacy `0000`–`0015` journal plus the same core guard, with its own catalogue and authorization gates. Optional creation/rendering remains held. A target with optional migrations already applied can receive the guard later only after its own row-compatibility and transaction prechecks pass.
4. **Fail-closed release evidence:** extend `check-migrations.mjs`, CI tests, `build-production.mjs`, `authorize-release.mjs`, receipts, and schema-lock format to bind the selected mode, both journal plans, source hashes, and exact catalogue. An unknown or skipped migration in either lane blocks release. Snapshot generation/checks must cover each lane; a future combined source needs an explicit core-only selection and an optional snapshot strategy rather than running the monolithic folder by default.
5. **Local proof matrix:** rehearse on disposable PostgreSQL 18.6 with synthetic data: fresh legacy `0000`–`0011` then guard; upgrade from original applied `0011`; guard before optional `0012`–`0015`; optional `0012`–`0015` before guard; malformed legacy/guard hashes; incompatible existing rows; validation failure and transaction recovery. Assert core mode creates no optional table and that both journals, constraint definitions, and catalogues match their separate reviewed expectations. Measure guard validation lock duration before any persistent migration proposal.

This track split preserves possible archived history without activating archived compute now. It has a real maintenance cost: two journals and mode-specific schema evidence for every future migration, coordinated generation when optional SQL touches core tables, and a target-specific convergence audit whenever an archived branch is reintroduced. No existing code or lock presently provides those guarantees.

## Remaining facts and bounded approval request

**Option A** depends on proving optional `0012`–`0015` unapplied across every target that will be supported; the five ready readbacks are insufficient. **Recommended B** does not need archived branches activated to preserve their existing migration identities. It still needs exact target identity, legacy journal, catalogue, and consent-row prechecks before that target is migrated or served. The active deployment-to-secret binding, archived branch contents, and undiscovered project inventory remain unknown; none is assumed clean.

Approve only a **local two-track proof of concept**: add explicit configs/runner/verifier prototypes and tests against disposable PostgreSQL 18.6 using synthetic data, while preserving both legacy SQL lineages and the core branch's optional-table absence. The proof should return a reviewed mode contract, journal/catalogue hashes, rollback behavior, and a list of files that a later production implementation would change. It would not authorize numbering or applying the guard on a persistent target, canonical lock capture, publication, deployment, or optional-feature enablement.

**Reversal:** deleting this documentation page reverses this turn's repository change. No migration, journal, snapshot, lock, database, or deployment was modified.
