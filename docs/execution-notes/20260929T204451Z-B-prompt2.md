## Diagnosis and implementation

The real DTO omitted tier/outputAccepted yet emitted download URLs from raw ready status. The browser required outputAccepted, so it hid real results while fixture responses supplied the missing flag. Direct downloads bypassed that browser-only check. New DTO regressions failed before the repair.

- Added one pure read-side acceptance predicate with version/policy/validator identity, exact account/job/canonical-path/hash/bytes binding and required media/check evidence. It never manufactures validation evidence.
- DTO derives Standard/Premium from server provider and exposes only the acceptance boolean plus owned URL. Internal evidence stays private. Existing identity sanitization remains intact.
- Finalize/status reports ready only for accepted available output. Download repeats the acceptance check before reading storage. Unaccepted ready is 202 status / 409 download; anonymous is 401, wrong owner 404, deleted is 410.
- Deleted accepted output remains terminal with no URL/actions; the browser labels it unavailable rather than processing.
- Ready notifications now require accepted, nondeleted, newly completed output; raw backend-ready no longer sends a false ready-to-download email.
- History already uses jobDto; no alternate fixture-only DTO added. No schema migration or dependency added. Existing `output` JSON persists the eventual evidence record.

Contract for the next lane: [OUTPUT-ACCEPTANCE-CONTRACT.md](../OUTPUT-ACCEPTANCE-CONTRACT.md). Current finishers do **not** produce this evidence. No backfill, refund, re-debit or synthetic signoff was performed. This local patch must not be deployed as a usable-render release before Prompt 3 implements validation and atomic acceptance/debit.
